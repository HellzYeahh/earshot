# Google Fast Pair as a cross-brand control channel for a third-party Android app (Earshot)

Researched 2026-10-20. Spec page dates are each page's "Last updated" footer as fetched that day.
Earshot rule applied throughout: anything that needs Google servers counts as unavailable (no INTERNET
permission). Licence of each source is given in brackets; GPL/AGPL/unlicensed sources are used for facts only.

## 1. Message Stream message groups and codes, and which ones need the account key / MAC

### Takeaway
The current spec defines eight message groups. A third-party app can use every message that is
**read-only or Provider-initiated**: model ID, BLE address, L/R/case battery with charging bit,
remaining time, active components (in-ear/worn), firmware version, ANC state with its supported modes,
and connection status. It can also send **Ring** and the **Get** requests, which need no MAC. **Set ANC** and
every Audio Switch (SASS) configuration write need an 8-byte HMAC-SHA256 MAC keyed by an
**account key**. The spec says the MAC exists so the headset can check that the sender is GMSCore and
not another app. So a non-Google app can read ANC but cannot change it, unless it puts its own
account key on the headset (see Inferences for why Earshot should not).

### Cited Findings
**Framing and transport**
- Message Stream = "additional channel for a persistent connection" to the Provider. When the Provider connects to a supported Seeker, the Seeker (phone) attempts to connect it. Transports: RFCOMM on fixed UUID `df21fe2c-2515-4fdb-8886-f12c4d67927c`, or L2CAP with the PSM read from a GATT characteristic. Frame = `group u8, code u8, length u16, data`; length and data big-endian. Page updated 2025-08-12. [CC-BY 4.0] — [Message Stream](https://developers.google.com/nearby/fast-pair/specifications/extensions/messagestream)
- The L2CAP variant (BLE / LE Audio devices) uses the Message Stream PSM characteristic `FE2C1239-8366-4814-8EB0-01DE32100BEA` with LE credit-based flow control. After a TWS role switch the Provider should drop the L2CAP link so the Seeker reconnects to the new primary. Source: search-result excerpt of the page, not fully fetched. [CC-BY 4.0] — [BLE Device](https://developers.google.com/nearby/fast-pair/specifications/bledevice)

**Group 0x01 Bluetooth event / 0x02 Companion app event** (not on the current spec pages I fetched; taken from Google's own ChromeOS Seeker)
- `0x01/0x01` enable silence mode, `0x01/0x02` disable silence mode (no data); `0x02/0x01` log buffer full (no data). [BSD-3, Chromium] — [fast_pair_data_parser.cc](https://chromium.googlesource.com/chromium/src/+/main/chromeos/ash/services/quick_pair/fast_pair_data_parser.cc)

**Group 0x03 Device information event** (Provider → Seeker unless noted; page updated 2026-09-09) [CC-BY 4.0] — [Device information](https://developers.google.com/nearby/fast-pair/specifications/extensions/deviceinformation)
- `0x01` Model ID: 3 bytes, sent when the Message Stream connects (used for retroactive account-key writing). Example `03 01 0003 AABBCC`.
- `0x02` BLE address updated: 6 bytes. Sent on connect and whenever the address rotates, if the Provider can obtain it.
- `0x03` Battery updated: 3 bytes L, R, case, in the same encoding as the advert (bit 7 = charging, bits 0–6 = 0–100 %, 0x7F = unknown). Sent on connect and on change. Example `03 03 0003 57 41 7F` = L 87 %, R 65 %, case unknown.
- `0x04` Remaining battery time: minutes, u8 or u16. Example `03 04 0001 F0` = 240 min.
- `0x05` Active components request (Seeker → Provider, no data); `0x06` response within 1 s. For buds: `00` none, `01` right active, `02` left, `03` both. For a single component: `00` unavailable, `01` active.
- `0x07` Capabilities: deprecated.
- `0x08` Platform type: `[platform, version]`, `01` = Android, version = SDK int (e.g. 0x1C = Pie). The spec lists it as Provider → Seeker. Chromium's parser only accepts platform 0x01. [BSD-3] — [fast_pair_data_parser.cc](https://chromium.googlesource.com/chromium/src/+/main/chromeos/ash/services/quick_pair/fast_pair_data_parser.cc)
- `0x09` Firmware version: UTF-8, same as the GATT Firmware Revision characteristic. Sent on connect; the Seeker compares it with its cache. [CC-BY 4.0] — [Change capability](https://developers.google.com/nearby/fast-pair/specifications/extensions/changecapability) (updated 2025-08-12)
- `0x0A` Session nonce: 8 bytes. Generated by the Provider once per connection and sent when the Message Stream connects. [CC-BY 4.0] — [MAC](https://developers.google.com/nearby/fast-pair/specifications/extensions/mac) (updated 2026-06-04)
- `0x0B` Current Find Hub Network (FHN) ephemeral ID: 4-byte clock + 20- or 32-byte EID, used to correct clock drift. — [Device information](https://developers.google.com/nearby/fast-pair/specifications/extensions/deviceinformation)

**Group 0x04 Device action** (page updated 2025-08-12) [CC-BY 4.0] — [Device action](https://developers.google.com/nearby/fast-pair/specifications/extensions/deviceaction)
- `0x01` Ring: byte 1 = component bits (`00` stop all, `01` ring right, `02` ring left, `03` both; single-component Providers use only bit 0). Optional byte 2 = timeout in seconds (`01 3C` = right, 60 s). The Provider must ACK. With no ACK within 1 s, or a NAK, the Seeker treats Ring as unsupported. The page gives no MAC requirement, and Chromium's parser accepts Ring with 1 or 2 data bytes.

**Group 0x06 Device capability sync** — `0x01` request capability update (Seeker → Provider). `0x03` FHN tracking reply (7 bytes: provisioning state `00` unprovisioned / `01` provisioned, plus the current 6-byte BLE MAC), sent only if FHN tracking is enabled. — [Change capability](https://developers.google.com/nearby/fast-pair/specifications/extensions/changecapability)

**Group 0x07 Audio Switch (formerly SASS, Smart Audio Source Switching)** (page updated 2025-08-12; needs GFPS v3.2+) [CC-BY 4.0] — [Audio Switch](https://developers.google.com/nearby/fast-pair/specifications/extensions/sass)
- No MAC: `0x10` get capability, `0x21` get switching preference, `0x22` notify switching preference, `0x32` notify multipoint-switch event (reason media/call, target, target device name UTF-8), `0x33` get connection status, `0x34` notify connection status (its contents are encrypted).
- MAC required: `0x11` notify capability (when sent by the Seeker), `0x12` set multipoint on/off, `0x20` set switching preference, `0x30` switch active audio source, `0x31` switch back, `0x40` notify "connection initiated by Audio Switch", `0x41` indicate in-use account key, `0x42` send custom data, `0x43` set drop-connection target. Rule: every Seeker → Provider message that carries data needs a MAC and gets an ACK/NAK.
- The Audio Switch advert carries a connection-status field encrypted with AES-CTR, with a key derived by HKDF from the **in-use account key**. So without an account key the status cannot be decrypted.

**Group 0x08 Hearable controls = ANC** (page updated 2026-06-29) [CC-BY 4.0] — [Hearable Controls](https://developers.google.com/nearby/fast-pair/specifications/extensions/hearablecontrols)
- `0x11` Get ANC state: Seeker → Provider, no MAC, no ACK.
- `0x12` Set ANC state: Seeker → Provider, **MAC required**, ACK required.
- `0x13` Notify ANC state: Provider → Seeker, no MAC. Sent on Seeker connect, in reply to Get, after every Set (to *all* connected Seekers), and when the user changes mode by gesture or in the vendor app.
- Notify payload (length 4): `[version=0x02, UI-toggle flags, settable flags, current-state flags]`, with exactly one bit set in the current state. Flag bits, bit 0 = MSB: bit 0 transparency, bit 1 adaptive, bit 2 off, bit 3 reserved, bit 4 ANC. "Settable" can be 0 while the buds are not worn (example 2 on the page).
- Set payload: length `0x04` or `0x14`, `[seeker version 01|02, UI-toggle flags, settable flags, new state]` plus 16 reserved bytes when the length is 0x14. Then the 8-byte message nonce and 8-byte MAC (MAC framing below).
- The page describes the Seeker (GMS) as owning the UI and logic to get, set and save ANC; the state is stored in the headset. Only ANC is defined: no EQ, spatial audio or ANC levels.

**Group 0xFF Acknowledgement** (page updated 2025-08-12) [CC-BY 4.0] — [Acknowledgement](https://developers.google.com/nearby/fast-pair/specifications/extensions/acknowledgement)
- `0x01` ACK `[group, code, current state…]`; `0x02` NAK `[reason, group, code, …]`, due within 1 s. NAK reasons: `00` not supported, `01` busy, `02` not allowed in current state, `03` **incorrect MAC**, `04` redundant action.

**MAC construction** [CC-BY 4.0] — [Message Authentication Code](https://developers.google.com/nearby/fast-pair/specifications/extensions/mac)
- Stated purpose: the Provider must check that configuration messages come from GMSCore (the Fast Pair module), not from another app on the phone.
- `MAC = first 8 bytes of HMAC-SHA256(K, session_nonce ‖ message_nonce ‖ additional_data)`, with `K = account_key ‖ 48 zero bytes`. The session nonce (8 B) comes from the Provider via `0x03/0x0A`. The message nonce (8 B) is random per message from the Seeker. Frame: `group, code, len+16, data, message nonce (8), MAC (8)`. The Provider tries every stored account key and NAKs with reason `03` on mismatch.

### Inferences
- **What a key-less third party can use:** all of 0x03 (battery L/R/case + charging, remaining time, worn state, model ID, firmware, BLE address), Ring (0x04/0x01), Get/Notify ANC (current mode plus which modes exist and which are settable now), and the unencrypted Audio Switch notifications (switch events, switching preference).
- **What it cannot use without an account key:** Set ANC, multipoint on/off, source switching, and decrypting the Audio Switch connection status.
- **Account keys are out of reach.** They are 16-byte secrets written by the Seeker (GMS). I found no public Android API that exposes them. The only route for a third party is to write *its own* key with Key-based Pairing, and that needs one of:
  - ECDH against the model's anti-spoofing public key. Google distributes that key with the model ID at registration, and the headset honours this path only in pairing mode ([GATT](https://developers.google.com/nearby/fast-pair/specifications/service/gatt), [Model registration](https://developers.google.com/nearby/fast-pair/specifications/service/modelregistration)).
  - The retroactive path: within 1 minute of a classic bond, and only one key ([Retroactive](https://developers.google.com/nearby/fast-pair/specifications/extensions/retroactiveacctkey)). The retroactive page does not say how the shared secret is set up; presumably it is the same anti-spoofing ECDH.

  An offline app has no supported way to get the per-model public keys.
- **Why writing a key is a bad idea anyway:**
  - It takes a slot in the headset's limited account-key list.
  - On a headset never paired with Android, the first key written becomes the **Owner** key, which governs Find Hub ([WhisperPair](https://whisperpair.eu/)).
  - Earshot should treat account-key writes like the BMAP firmware-update and authentication blocks: never.
- **Practical scope for Earshot:** battery, "is it worn", ring, ANC *read*, and switch-event notifications, for any certified Fast Pair headset. ANC *write* is not available through Fast Pair.

### Gaps
- Bluetooth event (0x01) and Companion app event (0x02) codes appear in Chromium's Seeker, but I did not find them on the current spec pages (they may have been dropped). Group `0x05` is not defined on any page I fetched.
- When Hearable Controls (0x08) entered the spec is not stated on the page; only the 2026-06-29 update date is known. Version code 0x02 implies at least one earlier revision.
- The spec does not say explicitly whether Ring needs a MAC. The MAC page names only Audio Switch configuration (and Hearable Controls marks Set ANC). That Ring works unauthenticated is inferred from the absence of a rule and from Chromium's parser, not tested.

## 2. Can an ordinary Android app open the Message Stream while Google Play services holds it?

### Takeaway
Nothing in the protocol stops a third party: no handshake, no authentication on reads. A non-Google,
non-Android client (BlueZ on Linux, in an unmerged patch) has read battery from Pixel Buds Pro this
way, and ChromeOS is a full non-Android Seeker. **On an Android phone with Google Play services,
though, the channel is very likely occupied.** The spec has the Seeker open a persistent stream as
soon as the headset connects, and the AOSP RFCOMM layer refuses a second client connection to the same
(server channel, device) with `PORT_ALREADY_OPENED`. I found **no report** of a third-party Android
app talking Message Stream, either succeeding or failing. Earshot has to test this on the Galaxy.

### Cited Findings
- The Seeker opens the stream itself when the Provider connects, and it is described as a persistent connection. [CC-BY 4.0] — [Message Stream](https://developers.google.com/nearby/fast-pair/specifications/extensions/messagestream)
- The retroactive account-key flow relies on the stream being opened for headsets paired through ordinary Bluetooth settings (the Provider sends model ID + BLE address once RFCOMM is up). So GMS connects the stream even for headsets that were never Fast Paired. [CC-BY 4.0] — [Retroactive account key](https://developers.google.com/nearby/fast-pair/specifications/extensions/retroactiveacctkey)
- AOSP Bluetooth stack, `RFCOMM_CreateConnectionWithSecurity`, comment: "On the client side, do not allow the same (dlci, bd_addr) to be opened twice by application". If an existing client port matches, the function returns `PORT_ALREADY_OPENED`. Server-side calls always allocate a new port. [Apache-2.0] — [port_api.cc (AOSP main)](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/stack/rfcomm/port_api.cc)
- **BlueZ patch (unmerged):** "[PATCH BlueZ v2 0/4] Add component batteries and Fast Pair Message Stream", by Matthias Kurz, 2026-08-21.
  - It adds an experimental RFCOMM-only Message Stream profile. The channel comes from SDP via the fixed UUID ("Pixel Buds Pro advertise the fixed UUID in SDP"). It parses only `0x03/0x03` battery and reconnects with back-off when the stream drops while BR/EDR stays up.
  - Tested only on Pixel Buds Pro; no account key or MAC involved.
  - Maintainer Luiz von Dentz (2026-09-01) questioned shipping "the proprietary Google FastPair" in BlueZ and suggested an external RegisterProfile layer instead.
  - [BlueZ is GPL-2.0: facts only] — [linux-bluetooth thread](https://ratatoskr.run/linux-bluetooth/2026/08/17446083/t)
- ChromeOS ("Quick Pair") is a non-Android Fast Pair Seeker in Chromium that parses Message Stream groups 0x01–0x04 and 0xFF (model ID, BLE address, battery, remaining time, active components, platform, ring, ACK/NAK). [BSD-3: code may be ported with attribution] — [fast_pair_data_parser.cc](https://chromium.googlesource.com/chromium/src/+/main/chromeos/ash/services/quick_pair/fast_pair_data_parser.cc)
- BlueZ issue #963 tentatively labels `df21fe2c-…` as "Google Fast Pair Service (GFPS)". [GPL] — [bluez/bluez#963](https://github.com/bluez/bluez/issues/963)
- microG / de-Googled phones: an /e/OS backlog issue asks for an open-source Fast Pair equivalent, possibly with microG. It is low priority and unimplemented, so I found no evidence that microG implements Fast Pair. — [e Foundation backlog #5464](https://gitlab.e.foundation/e/backlog/-/issues/5464)
- The Google Play services `com.google.android.gms.nearby.fastpair` client package exposes a `FastPairClient` and pairing status codes; the search excerpt shows no Message Stream API for apps (summary page not opened in full). — [GMS fastpair package summary](https://developers.google.com/android/reference/com/google/android/gms/nearby/fastpair/package-summary)
- Google's companion-app integration page offers only: a post-pairing app-install notification (extras `android.bluetooth.device.extra.DEVICE` and `com.google.android.gms.nearby.discovery.fastpair.MODEL_ID`), a firmware-update broadcast (`com.google.android.gms.nearby.fastpair.ACTION_FIRMWARE_UPDATE_BROADCAST`) and Settings slices. It describes no way for apps to share the Message Stream (updated 2026-10-05). [CC-BY 4.0] — [Companion apps](https://developers.google.com/nearby/fast-pair/companion-apps)

### Inferences
- **Why a second connection fails:** one phone has one RFCOMM multiplexer per ACL to the headset, so GMS and Earshot would need the same DLCI.
  - Android's stack rejects the second client connect (`PORT_ALREADY_OPENED`), so `BluetoothSocket.connect()` should throw.
  - Even without that check, RFCOMM allows only one DLC per DLCI per multiplexer.
- **When it might work:**
  - (a) Phones without GMS Fast Pair (AOSP/LineageOS without GApps, microG, Huawei).
  - (b) Before GMS connects, or after it drops the stream. Whether GMS keeps it open for the whole connection is unknown.
  - (c) The BLE L2CAP transport (LE Audio / BLE Providers). LE credit-based channels allow several channels to one PSM, so a second Seeker may be accepted. That depends on firmware and is untested.
- **The "Gets" are worth little to a non-GMS Seeker.** Notify ANC is pushed on Seeker connect and battery on connect and change, so a third party that cannot hold the stream gains almost nothing from the Gets.
- **Cheap test on the Galaxy (Earshot spike D5):** with a Fast Pair headset connected,
  - check `adb shell dumpsys bluetooth_manager` for an RFCOMM client socket owned by GMS on the `df21fe2c` channel;
  - then try `createInsecureRfcommSocketToServiceRecord(df21fe2c…)` from Earshot and log the error, then retry after force-stopping Play services (Bluetooth stays connected).
  - Expected result: the first attempt fails with an IOException while GMS holds the channel.
- **Code reference:** Chromium's BSD-licensed parser is the best permissive Seeker reference; its validation rules (exact byte counts, platform 0x01 only) can be ported with credit.

### Gaps
- No direct evidence, either way, of a third-party Android app opening the Message Stream on a GMS phone (searched Gadgetbridge, BudsLink, pbpctrl, LibrePods/CAPod, GitHub generally). Gadgetbridge (AGPL) does not appear to implement Fast Pair. pbpctrl (MIT/Apache) uses the Pixel Buds "Maestro" channel instead. LibrePods/CAPod (GPL) are AirPods-only (AAP), so Fast Pair is outside their scope.
- Whether GMS keeps the stream open for the whole connection, or closes it after reading model ID, battery and firmware, is undocumented.
- Whether Providers accept a second Seeker on the L2CAP Message Stream from the same phone is undocumented.

## 3. What a third-party app gets from Fast Pair BLE adverts without connecting, and matching to the connected headset

### Takeaway
Without connecting, an app with `BLUETOOTH_SCAN` sees two advert types on service UUID `0xFE2C`:
- **Pairing mode:** the 3-byte model ID only.
- **Normal mode:** a version byte, the account-key Bloom filter, a 2-byte salt and *optional* L/R/case battery (bit 7 = charging), with **no model ID**.

The battery may be shown only around case-open (the spec discourages advertising it all the time). Model ID → name/image needs Google's Nearby Devices API (network + API key), so Earshot can't use it. Without an account key an advert can't be tied to *your* headset: it comes from a rotating random address, and the filter needs the key. Matching stays a heuristic.

### Cited Findings
- **Discoverable (pairing-mode) advert:** service data `0xFE2C` = 24-bit model ID, interval ≤ 100 ms, BLE address must not rotate while discoverable. An LE Audio Sharing variant adds a version byte and an FP Capability Map (bit S = LE Audio Sharing, bit O = out-of-box/no account keys). Page updated 2026-09-30. [CC-BY 4.0] — [Provider advertising](https://developers.google.com/nearby/fast-pair/specifications/service/provider)
- **Not-discoverable advert:**
  - Layout: `0x00` flags, then Account Key Data (length/type nibble: `0000` show UI, `0010` hide UI), the filter, and Salt (type `0001`, 2 B). Interval ≤ 250 ms.
  - Advertised only if the headset holds ≥ 1 account key. No model ID.
  - Filter size `s = trunc(1.2n + 3)` bytes. For each key K, `SHA256(K ‖ salt)` gives eight u32 values Xi; set bit `Xi mod 8s`. False-positive rate well under 0.5 %.
  - Salt regenerated whenever the RPA rotates.
  - [CC-BY 4.0] — [Provider advertising](https://developers.google.com/nearby/fast-pair/specifications/service/provider)
- **Battery in adverts:**
  - Byte `LLLLTTTT`: L = count, T `0011` show UI / `0100` hide UI. Then up to 3 bytes `SVVVVVVV` (S = charging, V = 0–100, 0x7F unknown) for L, R, case.
  - When battery is present it is mixed into the filter hash (anti-tamper).
  - Optional. "To prevent tracking, the Provider should not include raw battery data in the advertisement all the time"; the example uses show-UI at case open and hide at bud removal or case close.
  - Updated 2026-06-04. [CC-BY 4.0] — [Battery Notification](https://developers.google.com/nearby/fast-pair/specifications/extensions/batterynotification)
- Model ID → name and picture: ChromeOS fetches `https://nearbydevices-pa.googleapis.com/v1/device/<id>?key=<API key>&mode=…&alt=proto`, described as "name and picture". [BSD-3] — [device_metadata_fetcher.cc](https://chromium.googlesource.com/chromium/src/+/main/ash/quick_pair/repository/fast_pair/device_metadata_fetcher.cc)
- Registration: Google issues the model ID and anti-spoofing key pair after Nearby Console approval; the registered name must contain brand + product. [CC-BY 4.0] — [Model registration](https://developers.google.com/nearby/fast-pair/specifications/service/modelregistration)
- Inside the Message Stream, `0x03/0x02` reports the current BLE address on connect and on rotation. This is the one spec-sanctioned link between the classic connection and the BLE adverts. — [Device information](https://developers.google.com/nearby/fast-pair/specifications/extensions/deviceinformation)

### Inferences
- **Name and image offline:** the only offline route is a bundled model-ID table, and that table could only be built from the online API or community lists. In normal operation the model ID isn't advertised at all, so it is seen only in pairing mode or via `0x03/0x01` on the stream (which needs the stream, see Q2).
- **Matching heuristic when the account-key filter can't be checked:**
  - an `0xFE2C` non-discoverable advert with battery, seen while a single Fast Pair-capable headset is connected over A2DP/HFP;
  - strong RSSI;
  - battery values consistent with `BATTERY_LEVEL_CHANGED`.

  With two Fast Pair headsets nearby (household, office) it will mis-attribute. Earshot should label the result "nearby Fast Pair battery", not the battery of the connected device.
- **How often battery appears:** spec-conforming earbuds put battery in adverts mainly around case-open, so the advert path gives a snapshot at case-open rather than a continuous gauge. Over-ear headphones don't do Battery Notification at all (Q4), so for them adverts give nothing beyond presence.
- **Identification:** a headset whose SDP record lists `df21fe2c-…` is Fast Pair capable. That is a cheap identification signal for Earshot's planned `DeviceIdentifier` (roadmap A2), and it needs no connection beyond `fetchUuidsWithSdp`.

### Gaps
- Whether Android's scanner reports a bonded headset's LE identity address instead of its RPA in `ScanResult` was not checked; that would make matching deterministic for LE-bonded (CTKD) headsets.
- How often real products include battery in adverts outside case-open is unmeasured.
- Whether the Nearby Devices API response includes the anti-spoofing public key is not confirmed by the Chromium file read.

## 4. Which brands/models implement Fast Pair with Message Stream and ANC messages; rough reach

### Takeaway
**Message Stream is mandatory** for every certified Fast Pair hearable (GFPS v3.1+): device information and Ring for all, plus L/R/case battery for earbuds. That covers essentially every Android-oriented brand: Sony, JBL, Jabra, Marshall, Xiaomi/Redmi, Nothing/CMF, OnePlus, Soundcore, Logitech, Google, Bose QC Earbuds, realme, EarFun. Reach is hundreds of millions of devices. **ANC over Fast Pair (Hearable Controls) is optional, earbuds-only, and turned on per model in Google's console**. The only confirmed users are Pixel Buds Pro / Pro 2. I found no non-Google product confirmed to implement it.

### Cited Findings
- **Hearables requirements** (updated 2026-10-05) [CC-BY 4.0] — [Hearables device feature requirements](https://developers.google.com/nearby/fast-pair/specifications/devicefeaturerequirement/devicefeaturerequirement_hearables)
  - Minimum GFPS v3.1.
  - Mandatory for TWS earbuds: Message Stream with Device Information + Device Action (Ring), Battery Notification L/R/case + charging, Personalized Name, Retroactive Pairing, firmware version (GATT or Message Stream).
  - Optional for earbuds: Audio Switch (v3.2+, needs MAC + ACK), **Hearable Controls**, Find Hub Network, LE Audio Sharing.
  - Headphones (over-ear): same mandatory core, but Battery Notification "not supported", and Hearable Controls is not listed.
  - Hearable Controls is enabled with the console option "Support ANC Slice on Fast Pair".
- WhisperPair (KU Leuven COSIC/DistriNet, IEEE S&P 2026, CVE-2025-36911, reported to Google in August 2025) found Key-based Pairing accepted outside pairing mode on devices that passed Google certification, affecting "hundreds of millions of users". — [whisperpair.eu](https://whisperpair.eu/)
- Devices the WhisperPair researchers listed as vulnerable (therefore Fast Pair implementers): Soundcore Liberty 4 NC, Pixel Buds Pro 2, JBL Tune Beam, Jabra Elite Active, Marshall Motif II A.N.C., Nothing Ear (a), OnePlus Nord Buds 3 Pro, Sony WF-1000XM5, WH-1000XM4, WH-1000XM5, WH-1000XM6, WH-CH720N, Redmi Buds 5 Pro. Reports cite 17 devices from 10 brands, including Logitech. Counts differ between outlets (15 manufacturers in another). — [Malwarebytes, 2026-01](https://www.malwarebytes.com/es/blog/news/2026/01/whisperpair-exposes-bluetooth-earbuds-and-headphones-to-tracking-and-eavesdropping); [Tom's Guide](https://www.tomsguide.com/audio/headphones/hundreds-of-millions-of-earbuds-headphones-and-speakers-vulnerable-to-tracking-and-eavesdropping-what-to-do-right-now)
- **Seen in the wild** (BlueZ dumps posted to BudsLink, GPL-3.0, facts only): the Bose QC Ultra Earbuds (modalias `v009Ep4072` = scotty, issue opened 2026-05-16) list `df21fe2c-…` in SDP next to `00000000-deca-fade-deca-deafdecacaff` and Qualcomm-base UUIDs `0000eb04/eb06/eb07-d102-11e1-9b23-00025b00a5a5`. — [BudsLink #36](https://github.com/maniacx/BudsLink/issues/36)
- Search-index hits show the same UUID in BudsLink reports for CMF Buds Pro 2, Nothing Ear (3a), realme Buds T200x, Redmi Buds 6 Play and REDMI Buds 8 Lite (not opened individually). — [#31](https://github.com/maniacx/BudsLink/issues/31), [#128](https://github.com/maniacx/BudsLink/issues/128), [#134](https://github.com/maniacx/BudsLink/issues/134), [#46](https://github.com/maniacx/BudsLink/issues/46), [#79](https://github.com/maniacx/BudsLink/issues/79)
- Pixel Buds Pro advertise the Message Stream UUID in SDP and send battery over it (BlueZ patch test). — [linux-bluetooth thread](https://ratatoskr.run/linux-bluetooth/2026/08/17446083/t)
- **Pixel ANC UI:**
  - Pixel Buds noise-control options appear only while the buds are actively connected; Adaptive is Pixel Buds Pro 2 only. — [Pixel Buds Help](https://support.google.com/googlepixelbuds/answer/7685360)
  - The ANC/spatial controls in the Android 15 beta volume panel "only worked for the Pixel Buds Pro" and Pro 2. — [PhoneArena](https://www.phonearena.com/news/android-15-might-return-anc-controls-to-the-volume-panel_id161781)

### Inferences
- **Battery reach:** every certified Fast Pair TWS earbud of the last few years should push L/R/case battery and support Ring over the Message Stream. That includes the Bose QC Ultra Earbuds, so it is relevant even inside Earshot's Bose catalogue.
- **ANC reach:** ANC read via `0x08` is probably limited to Pixel Buds Pro / Pro 2 plus any OEM that turned on the console flag. Since the requirements page doesn't list Hearable Controls for over-ears, Sony WH-1000XM*, the Bose QC Ultra Headphones and similar headphones shouldn't be expected to answer `0x08`. For a "universal ANC remote", Fast Pair adds little; vendor protocols remain necessary.
- **Over-ear headphones** get Device Information (model ID, firmware) and Ring but no battery notification under the certification rules, so Fast Pair adds almost nothing for them beyond what `BATTERY_LEVEL_CHANGED` already gives.

### Gaps
- No public list of models that enabled Hearable Controls ("ANC slice") exists that I could find. I can't confirm any non-Google product implements `0x08`.
- Whether the user's QC Ultra Headphones 2nd Gen expose `df21fe2c` in SDP is unknown: no Earshot capture contains it. A `fetchUuidsWithSdp` dump on the Galaxy would answer it.
- Market-share figures for Fast Pair-enabled headsets were not found. "Hundreds of millions" is the researchers' own estimate.

## 5. Spec licence terms and any certification/policy restriction on non-Google apps

### Takeaway
The spec text is **CC-BY 4.0** and its code samples **Apache-2.0**, so implementing the Seeker side
from the documentation is fine for an MIT app with attribution. Google's own Seeker parsers in Chromium
are **BSD-3** and AOSP is **Apache-2.0**, both portable with credit. Certification and the Nearby Console
govern *Providers* (headset makers). There is no third-party Seeker programme or policy, but
the protocol itself reserves all configuration writes for GMSCore through the account-key MAC, and the
metadata and anti-spoofing keys sit behind Google's online API.

### Cited Findings
- Spec pages: "content of this page is licensed under the Creative Commons Attribution 4.0 License", code samples Apache 2.0 (footer on Message Stream, MAC, Hearable Controls, Model registration). — [Message Stream](https://developers.google.com/nearby/fast-pair/specifications/extensions/messagestream); [Model registration](https://developers.google.com/nearby/fast-pair/specifications/service/modelregistration)
- Model registration needs a Google Cloud project and Nearby Console approval; the device name must include brand + product. This governs Providers only; the page says nothing about Seekers. — [Model registration](https://developers.google.com/nearby/fast-pair/specifications/service/modelregistration)
- Companion-app features (install prompt, firmware intent, slices) "are required for Certification and are tested", and companion apps are registered by package name in the Nearby Console. This is a Provider-side obligation. — [Companion apps](https://developers.google.com/nearby/fast-pair/companion-apps)
- The MAC extension exists so the Provider can confirm configuration messages come from GMSCore and not from another app. — [MAC](https://developers.google.com/nearby/fast-pair/specifications/extensions/mac)
- Chromium Quick Pair sources: "BSD-style license". — [fast_pair_data_parser.cc](https://chromium.googlesource.com/chromium/src/+/main/chromeos/ash/services/quick_pair/fast_pair_data_parser.cc)
- AOSP Bluetooth stack: Apache-2.0 (Broadcom 1999-2012 header). — [port_api.cc](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/system/stack/rfcomm/port_api.cc)
- The BlueZ maintainer's reluctance to carry "proprietary" Fast Pair in the stack was about maintenance, not legal terms. — [linux-bluetooth thread](https://ratatoskr.run/linux-bluetooth/2026/08/17446083/t)

### Inferences
- **Licensing:** no barrier to Earshot reading the Message Stream or adverts.
  - The spec is CC-BY: credit "Google Fast Pair specification, CC-BY 4.0" in `docs/reference/` and About, like bosectl.
  - Chromium code can be ported under BSD-3 with its notice.
  - Use "Fast Pair" descriptively only ("reads battery from Fast Pair headsets"). It is a Google feature name; trademark terms were not checked.
- **Policy:** the real restrictions are technical.
  - (1) GMS probably holds the RFCOMM channel (Q2).
  - (2) Writes need an account key, which by design only GMS has (Q1).
  - (3) Model metadata and anti-spoofing keys require Google's online API (Q3), which breaks Earshot's no-INTERNET rule.
- **Roadmap E4:** "Fast Pair baseline: battery L/R/case and ring for any Fast Pair headset" is protocol-legal. It is practically usable only (a) from adverts (battery snapshot, heuristic match) on every phone, and (b) over the Message Stream on phones where GMS doesn't occupy it. Treat it as a fallback tier, and gate the Message Stream path on a successful connect rather than assuming it.

### Gaps
- I did not find Google Play / Fast Pair terms that explicitly forbid a non-Google app from acting as a Seeker. I also found none that explicitly allow it.
- The Fast Pair trademark/branding rules for third-party apps were not located.
